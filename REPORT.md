## 1. Тема, номер і варіант

У лабораторній роботі № 2 я продовжив програму обліку автозапчастин із ЛР1. Перебудував предметну частину з використанням класу `SparePart` і record `StockValue`. 

## 2. Мета роботи

Перебудувати предметну частину продукту з лабораторної роботи № 1: замість рядків і паралельних змінних використати власні класи, перевірку стану об'єктів, record для незмінного допоміжного значення та тести, які підтверджують збереження поведінки.

## 3. Стан до і після

У ЛР1 `InventoryReport` одночасно розбирав рядок, перевіряв його поля й обчислював підсумки. У ЛР2 я розділив ці обов'язки між сутністю, фабрикою та звітним алгоритмом.

| Частина | ЛР1 | ЛР2 |
| --- | --- | --- |
| Запис | Масив рядків і доступ за індексами | Незмінний об'єкт `SparePart` |
| Розбір CSV | Методи `InventoryReport` | `SparePart.fromCsv` |
| Інваріанти | Умови у звітному алгоритмі | Конструктор `SparePart` |
| Підсумки | Окремі числові змінні | `StockValue(long stock, double value)` |
| CLI | Перевірки й запуск у Main | ArgumentParser та InventoryController |
| Версія | Число в POM і літерал у Java | POM → Maven-ресурс → ApplicationInfo |

Для запуску я залишив Main коротким: він готує UTF-8-потоки, викликає контролер і повертає код завершення. Парсер перевіряє параметри, контролер керує читанням, побудовою звіту та записом. Файлові операції виконує FileReport.

## 4. Клас-сутність

Для автозапчастини я використав окремий `final` клас `SparePart` із п'ятьма полями:

| Поле | Тип | Правило |
| --- | --- | --- |
| sku | String | Артикул не може бути null або порожнім |
| name | String | Назва не може бути null або порожньою |
| stock | int | Запас від 0 до Integer.MAX_VALUE |
| unitPrice | double | Невід'ємна скінченна ціна |
| supplier | String | Постачальник не може бути null або порожнім |

У конструкторі я перевіряю текст через `Objects.requireNonNull` та `isBlank`, прибираю крайові пробіли й відхиляю від'ємні числа. Для ціни перевіряю `Double.isFinite`, щоб не прийняти NaN або нескінченність. Нульові запас і ціна допустимі; -0.0 нормалізується до 0.0.

Методи `sku()`, `name()`, `stock()`, `unitPrice()` і `supplier()` повертають значення полів. Я оголосив усі поля як `private final` і не додавав сеттерів. У `toString()` ціна виводиться з двома десятковими знаками через `Locale.ROOT`.

## 5. Фабричний метод і record

Метод `SparePart.fromCsv(String line)` створює об'єкт із рядка `sku;name;stock;unitPrice;supplier`. Я зберіг роздільник `;`, UTF-8 та десяткову крапку. `split(";", -1)` зберігає порожнє останнє поле, щоб виявляти відсутнього постачальника.

Я обрав порядок «спочатку формат, потім валідність». Фабрика перевіряє кількість і заповненість полів, прибирає крайові пробіли й перетворює stock на int, а unitPrice на double. Після цього конструктор перевіряє допустимість значень. Його перевірки діють і за прямого створення об'єкта без CSV.

Наприклад, `a;b;-1;abc;s` дає помилку формату unitPrice. У рядку `a;b;-1;2;s` формат чисел правильний, тому конструктор повідомляє про від'ємний stock. Номер рядка додає InventoryReport, який також обробляє BOM на початку файла.

Для підсумків я використав `StockValue(long stock, double value)`. Record зберігає загальний запас і вартість, перевіряє їхню невід'ємність та скінченність вартості. Тип long дозволяє підсумовувати запаси, сума яких перевищує діапазон int.

Перед прийняттям запису InventoryReport обчислює майбутній підсумок і перевіряє переповнення. Лише після цього додає SparePart до списку й замінює підсумок. Хибний рядок не змінює статистику; програма записує причину та переходить до наступного рядка.

## 7. Інфраструктура

Я зберіг Maven Wrapper, JUnit 5, SpotBugs, Shade і workflow з ЛР1. Версію продукту залишив лише в `pom.xml`. Maven filtering підставляє `${project.version}` у `application.properties`, а ApplicationInfo читає значення для `--version`.

Для JAR я обрав сталу назву `autoparts-all.jar`. У POM я задав `finalName` основного артефакту й узгодив назву виконуваного JAR у Shade. Після зміни версії команди запуску залишаються такими самими. Назва JAR у довідці також береться з метаданих збірки.

Windows PowerShell:

```powershell
java --version

.\mvnw.cmd -B clean verify
java -jar target/autoparts-all.jar
java -jar target/autoparts-all.jar --help
java -jar target/autoparts-all.jar --version
```

macOS / Ubuntu:

```sh
chmod +x mvnw
./mvnw -B clean verify
java -jar target/autoparts-all.jar
```

Локальна збірка на Windows завершилася успішно: 66 тестів пройшли, SpotBugs не виявив проблем. Фази test і package виконані всередині verify. Javadoc перевіряється командою:


## 9. Порівняння поведінки

Для порівняння я використав `src/test/resources/lab01/input.csv` та `report.txt`, збережені до перебудови. Тест нормалізує тільки CRLF/LF; решта тексту має збігатися.

Контрольний результат:

```text
Склад автозапчастин — звіт
Коректних записів: 3
Загальна кількість деталей: 34
Вартість запасу: 8800.00 грн
Найдорожча деталь: SKU-002 — Brake discs; ціна: 1200.00 грн
Помилок: 2
Рядок 4: stock не може бути від'ємним
Рядок 5: stock має бути цілим числом у діапазоні int
```

Розрахунок: 10 + 4 + 20 = 34; 10 × 250 + 4 × 1200 + 20 × 75 = 8800. За однакової максимальної ціни я залишив вибір першого коректного запису. Повторні артикули рахуються окремо.

Формули й контрольний звіт я зберіг. На рядках із кількома дефектами перше повідомлення може відрізнятися від ЛР1 через обраний порядок «формат, потім валідність». Це рішення закріплено окремим тестом.

## 11. Відповіді на контрольні питання

1. Клас-сутність об'єднує дані запису й операції над ними, на відміну від рядка та індексів.
2. `private` приховує поле, `final` забороняє змінювати його після конструктора.
3. Інкапсуляція обмежує доступ до стану й не дозволяє обійти перевірки.
4. Конструктор перевіряє інваріанти при кожному створенні об'єкта.
5. `requireNonNull` відхиляє відсутнє посилання, `isBlank` — порожній або пробільний текст.
6. Без сеттерів об'єкт не переходить у неперевірений стан після створення.
7. Record автоматично має доступори компонентів, конструктор, `equals`, `hashCode` і `toString`.
8. Record призначений для компактного значення; клас-сутність дозволяє явно описати інваріанти й API домену.
9. Record не копіює змінний компонент, тому список усередині нього може змінюватися.
10. `fromCsv` називає спосіб створення та приховує деталі розбору.
11. Помилку одного рядка перехоплює цикл із номером рядка, аби продовжити файл.
12. Перевірка до додавання не дає хибному об'єкту вплинути на список чи підсумок.
13. `toString` призначений для читання об'єкта, CSV має окремий точний формат.
14. `Locale.ROOT` забезпечує стабільну крапку в числовому форматі незалежно від ОС.
15. AAA означає підготовку даних, виконання дії, перевірку результату.
16. Перевіряють null, порожні назви, від'ємні числа, NaN/Infinity та допустимі нулі.
17. Однаковий контрольний CSV і повне порівняння звітів до та після доводять сумісність.
18. Старі тести фіксують уже наявну поведінку й виявляють регресії під час рефакторингу.
19. Wrapper, POM, JUnit, аналізатор, JAR-конфігурація та workflow успадковуються з ЛР1.
20. Рядок `private final int stock;` приховує поле й забороняє його переприсвоєння після конструктора. Разом із перевіркою конструктора та відсутністю сеттера він захищає стан моєї сутності SparePart.
