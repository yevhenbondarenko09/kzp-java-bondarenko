## 4. Контракт даних

Спільний тип — незмінний абстрактний `SparePart`. Підтипи `OriginalPart` і `ReplacementPart` обчислюють гарантійний резерв як 10% і 5% ціни одиниці. `PartKind` містить ORIGINAL/REPLACEMENT. Текстові поля непорожні, запас невід’ємний `int`, ціна — скінченний невід’ємний `double`. Сума запасу — `long`.

Формат CSV UTF-8 без заголовка:

```text
sku;name;stock;unitPrice;supplier[;kind]
```

Для ЛР4 п’яте поле використовую як виробника. Технічне ім’я `supplier`, сигнатури конструкторів і формат CSV зберіг для сумісності з попередніми роботами.

Контракт рівності — конкретний підтип і SKU. Список зберігає всі записи; `distinct()` застосовується лише для окремого підрахунку унікальних деталей. Пошук за SKU може повернути перший запис будь-якого підтипу.

Методи приймають список валідних деталей без null; null для списку та ключа пошуку відхиляється. Вхідні об’єкти й порядок списку не змінюються. Кожен незалежний запит створює власний Stream.

Контрольний набір `src/test/resources/lab04/input.csv` і його копія для запуску `data/lab04.csv`:

| --- | --- | --- | --- | --- | --- | --- |
| 1 | A | Фільтр | 4 | 100 | Bosch | ORIGINAL |
| 2 | B | Колодки | 5 | 300 | Brembo | REPLACEMENT |
| 3 | C | Диск | 6 | 300 | Brembo | ORIGINAL |
| 4 | D | Лампа | 0 | 50 | Bosch | REPLACEMENT |
| 5 | E | Свічка | 1 | 0 | Denso | ORIGINAL |
| 6 | F | Ремінь | 6 | 200 | Denso | REPLACEMENT |

Поріг залишку зафіксовано як 5, N = 5. У наборі є 4/5/6 по різні боки порога, нульова ціна й запас, рівні ціни, повна нічия сортування, логічний дублікат і повтор SKU між підтипами. Очікувані суми обчислені з таблиці незалежно від реалізації запитів.

## 5. П’ять запитів

Джерело кожного запиту — `List<SparePart>` після валідації. Запити розміщені в `InventoryQueries`.

| --- | --- | --- | --- |

| `skus(parts)` | `map(SparePart::sku)` | `toList()` / List рядків | A, B, C, D, E, F, A, A |

## 6. Групування та статистика

Ключ групування — назва виробника типу `String`, взята з погодженого п’ятого поля. TreeMap забезпечує стабільний порядок назв. Вартість запасу в групі дорівнює сумі добутків запасу на ціну:

```text
Bosch = 4*100 + 0*50 + 4*100 + 2*150 = 1100
Brembo = 5*300 + 6*300 = 3300
Denso = 1*0 + 6*200 = 1200
Разом = 5600
```

Ціни 100, 300, 300, 50, 0, 200, 100, 150 дають суму 1200 і середнє 150. Статистика не зважує ціну запасом: запис із нульовим запасом теж входить до count і середнього. Групування відхиляє нескінченний добуток або підсумок; статистика відхиляє переповнення суми цін.

Для порожнього списку групування дає порожню карту. Статистика має count = 0, sum = 0, average = 0; стандартні min/max дорівнюють +Infinity/-Infinity, тому при відображенні спочатку перевіряється count:

```java
DoubleSummaryStatistics statistics = InventoryQueries.priceStatistics(List.of());
String minimum = statistics.getCount() == 0 ? "немає даних"
        : String.format(Locale.ROOT, "%.2f", statistics.getMin());
```

Для порожньої статистики результат цього прикладу — «немає даних». Числа у звіті й прикладах форматуються через Locale.ROOT, з десятковою крапкою. Для double у числових перевірках використано допуск 1e-9; повний текст старого звіту перевіряється точно з нормалізацією CRLF/LF.

## 7. Компаратор

```java
Comparator.comparingDouble(SparePart::unitPrice).reversed()
        .thenComparing(SparePart::name)
```

Ціна сортується за спаданням, а назва за зростанням стандартного порядку String. `reversed()` застосовано до ціни до додавання другого критерію. `sorted()` передує `limit()`, щоб відібрати найдорожчі з усього набору. Повна нічия зберігає порядок вхідного List.

`n < 0` відхиляється через IllegalArgumentException, `n = 0` повертає порожній список, завелике N — всі записи. На восьми записах top-5 відкидає три записи. У старому звіті діє окремий контракт: перший максимум B зберігається, навіть якщо за назвами C передує B. Для нього використано `min` зі спадним компаратором лише ціни.

## 8. Optional

`findBySku(parts, sku)` порівнює артикул точно й повертає `findFirst()`. Для A результатом є перший OriginalPart у вхідному списку. У тесті використав `assertSame`, бо equals не розрізняє повторені записи одного підтипу.

```java
String found = InventoryQueries.findBySku(parts, "A")
        .map(SparePart::name).orElse("не знайдено");
```

Для контрольного набору found = «Фільтр». Для `missing` або порожнього списку повертається Optional.empty(); get() без перевірки не використовується. Регістр і пробіли в ключі не змінюються неявно.

## 13. Порівняння реалізацій

У `lowStock` умову запасу видно в одному filter. У групуванні поруч записані ключ виробника й формула `stock * unitPrice`. Кожен метод я можу перевірити окремо від читання CSV та форматування звіту. Гарантійна сума викликає той самий поліморфний `warrantyCost()`.

Швидкість реалізацій я не вимірював. Top-N сортує весь список за O(n log n), filter і map проходять його за O(n). TreeMap впорядковує ключі групування. Кожен незалежний запит знову проходить список; для цього набору я залишив окремі короткі методи.

Паралельні потоки, власний Collector, дворівневе групування й бенчмарки не потрібні для рівня 2.

## 15. Відповіді на контрольні питання

1. Колекція зберігає елементи; потік описує одноразове обчислення над джерелом.
2. Конвеєр має джерело, проміжні операції й кінцеву операцію, наприклад parts → filter → toList.
3. Проміжні операції ліниві: без кінцевої операції обхід не запускається.
4. filter залишає елементи, для яких Predicate повернув true; у роботі це stock < threshold.
5. map повертає об’єктний потік іншого типу; mapToDouble — числовий DoubleStream із sum/average без пакування кожного числа.
6. distinct видаляє дублікати за equals/hashCode. У цій моделі ключ — підтип і SKU, а не всі поля.
7. sorted().limit(N) відбирає N із повністю впорядкованого джерела; limit(N).sorted() сортує лише перші N вхідних записів.
8. Кінцева операція запускає обчислення й дає список, число, карту, Optional або інший результат.
9. Collectors.joining об’єднує рядки з роздільником і, за потреби, префіксом та суфіксом.
10. groupingBy обчислює ключ для кожного запису та передає записи з однаковим ключем downstream-колектору.
11. Для суми в кожній групі використовується groupingBy(key, summingDouble(value)); у роботі value = stock * unitPrice.
12. DoubleSummaryStatistics містить count, sum, min, max і average.
13. Для порожнього потоку count/sum/average дорівнюють нулю, min = +Infinity, max = -Infinity. Відсутність мінімуму/максимуму потрібно пояснити при відображенні.
14. comparingDouble задає перший критерій, thenComparing — наступний на випадок рівності.
15. reversed після thenComparing розверне обидва критерії. У роботі потрібно розвернути лише ціну, зберігши назву за зростанням.
16. Optional явно показує, що результат може бути відсутній, замість неочевидного null.
17. orElse повертає готове запасне значення, orElseThrow викидає виняток за відсутності, ifPresent виконує дію лише за наявності.
18. Зовнішній змінний список у forEach приховує накопичення й ускладнює безпеку паралельного виконання; toList/collect явно описують результат.
19. Потрібно зберегти значення, порядок, дублікати, порожній випадок, обробку помилок, межі N і незмінність входу; старі тести мають пройти.
20. Паралельний потік може допомогти на великому наборі з незалежними дорогими операціями після вимірювань. Для малого CSV накладні витрати можуть бути більшими за виграш.

## 16. Висновки

На контрольному наборі я отримав ті самі результати циклом і через Stream API. Старий звіт зберіг перший максимум B, а top-5 поставив C перед B за назвою. У наступній роботі можна використовувати `InventoryQueries` для запитів до вже перевірених деталей без повторного розбору CSV.
