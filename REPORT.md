## 4. Repository<T>

Сховище має внутрішній `List<T>`. Параметр `T` задає тип записів: `Repository<SparePart>` приймає деталі обох підтипів, а `Repository<SparePartRecord>` зберігає записи для експорту. Компілятор перевіряє тип під час додавання; приведень типів у коді сховища немає.

`add` відхиляє null і зберігає порядок та повтори. `all()` повертає `List.copyOf(items)`: зовнішній код не може змінити цей список, а наступне додавання у сховище не змінює вже отриманий знімок. `find(Predicate<? super T>)` повертає незмінний список збігів. Предикат супертипу також допустимий; тест перевіряє Predicate<Number> для Repository<Integer>.

```java
Repository<SparePartRecord> repository = new Repository<>();
SparePartRecord.read(Path.of("data", "lab05.csv")).forEach(repository::add);
List<SparePartRecord> found = repository.find(part -> part.article().equals("C"));
```

У контрольному наборі пошук повертає запис C зі свічкою. Знімок захищає структуру списку; об’єкти предметних моделей у цьому проєкті теж незмінні.

## 5. Модель даних

За варіантом 4 клас запису має назву `SparePartRecord` і п’ять полів:

| Поле | Тип | Інваріант |
| --- | --- | --- |
| article | String | Непорожній артикул |
| name | String | Непорожня назва |
| quantity | int | Кількість не менша нуля |
| price | double | Скінченна ціна не менша нуля |
| manufacturer | String | Непорожня назва виробника |

Ключ пошуку за умовою варіанта — `article`. Методи `equals` і `hashCode` для record генерує компілятор; вони враховують усі п’ять полів. Тому порівняння початкового й відновленого списків виявляє зміну назви, кількості, ціни або виробника навіть за однакового артикулу. Повтори артикулів зберігаються.

Текст перевіряю через isBlank без обрізання пробілів чи перенесень. Числа перевіряю в компактному конструкторі, від’ємний нуль ціни нормалізую до нуля. Для експорту старих деталей `fromPart` переносить sku → article, stock → quantity, unitPrice → price, supplier → manufacturer.

Модель `SparePart`, її підтипи й `PartKind` зберіг. Експорт містить п’ять полів `SparePartRecord`; категорія `kind` залишається в початковому файлі. Під час round-trip порівнюються саме записи `SparePartRecord`.

## 6. @CsvColumn

Анотація має `@Retention(RetentionPolicy.RUNTIME)`, `@Target(ElementType.FIELD)` і метод `String value()`. Її додано до компонентів record; компілятор переносить анотацію з FIELD-target на відповідні приватні поля. Тест через рефлексію знаходить усі п’ять колонок.

Назви заголовків беруться з value, порядок визначається Java-іменами полів:

| Java-поле | CSV-заголовок |
| --- | --- |
| article | артикул |
| manufacturer | виробник |
| name | назва |
| price | ціна |
| quantity | кількість |

## 7. Рефлексивний експортер

У `CsvExporter.write(Path, Class<T>, List<? extends T>)` передаю клас запису окремим аргументом. З нього експортер отримує список колонок і формує заголовок навіть для порожнього списку.

Експортер отримує поля класу та його базових класів до `Object`, відбирає поля з `@CsvColumn` і сортує їх за Java-іменами. Доступ до приватних полів перевіряє через `trySetAccessible()`. Один список полів задає порядок і заголовків, і значень. Код експортера працює через `Class<T>` та `Field`, без звернень до конкретного предметного класу.

Перед записом перевіряються наявність колонок, непорожні й неповторні заголовки, відсутність статичних колонок і повторних Java-імен, типи записів та null-записи. Значення null у полі перетворюється на порожній текст; предметний SparePartRecord null не дозволяє. Помилки доступу зберігаються як cause.

Спочатку формується весь текст. Потім Files створює батьківські каталоги та записує UTF-8 файл із перезаписом старого вмісту. Тест підтверджує, що null-запис після коректного запису або хибна схема не змінюють наявний файл. Вхідний список і його об’єкти експортер не змінює.

У `CsvExporterTest` той самий експортер записує тип `Other` із рядком та `PartKind`. Інший тест експортує `Child` із приватним анотованим полем базового класу `Parent`.

## 8. Формат CSV

CSV ЛР5 має коми як роздільники, заголовок, UTF-8 і LF між записами. Поля з комою, лапкою, CR або LF беруться в подвійні лапки; внутрішня лапка подвоюється. Заголовок екранується за тими самими правилами.

Повний контрольний файл `data/lab05.csv`:

```csv
артикул,виробник,назва,ціна,кількість
A,Bosch,Фільтр,100.0,4
B,Brembo,"Колодки, передні",300.25,5
C,Denso,"Свічка ""Іскра""",0.0,0
D,Osram,"Лампа
фари",50.5,2
E,Bosch,Ремінь,200.0,6
```

П’ять записів займають сім фізичних рядків разом із заголовком. У D назва має перенесення. Тестова копія лежить у `src/test/resources/lab05/input.csv`; окремо збережені `invalid.csv` із хибною кількістю та нульовий за довжиною `empty.csv`.

Числа експортуються стандартним текстовим представленням double, яке не залежить від системної локалі й дозволяє відновити значення. Старий вхід звіту з роздільником `;` і необов’язковим kind залишається окремим форматом.

## 9. Імпорт і round-trip

`SparePartRecord.read(Path)` читає весь файл через `Files.readString(..., UTF_8)`. `CsvParser.parseDocument` повертає логічні записи: перенесення всередині лапок залишаються в полі. Парсер приймає LF, CRLF і CR, подвоєні лапки та необов’язковий BOM на початку. Пошкоджені лапки відхиляє.

Імпорт перевіряє точний заголовок, після чого `fromFields` перетворює кількість на `int`, ціну на `double` та викликає конструктор. `fromCsv` приймає один логічний запис без заголовка, у тому числі з багаторядковим полем. Порожній файл і файл лише із заголовком повертають порожній список.

```java
List<SparePartRecord> original = SparePartRecord.read(Path.of("data", "lab05.csv"));
CsvExporter.write(Path.of("out", "parts.csv"), SparePartRecord.class, original);
List<SparePartRecord> restored = SparePartRecord.read(Path.of("out", "parts.csv"));
System.out.println(original.size());
System.out.println(restored.size());
System.out.println(original.equals(restored));
```

Результат для `data/lab05.csv`:

```text
5
5
true
```

Порівняння через `equals` перевіряє всі поля, повтори й порядок записів. Збігаються також хеш-коди списків. Тест `roundTripMatchesFixtureAllFieldsOrderAndRepositorySearch` додатково починає з об’єктів, створених у Java, і порівнює експорт із CSV-еталоном. Інший тест перевіряє різні записи з однаковим артикулом, пробіли в тексті, повтори й `Double.MIN_VALUE`.

## 10. Помилки

`DataStorageException` є checked exception. Він має конструктор із повідомленням і конструктор із повідомленням та cause. Помилки імпорту не перетворюються на порожній список.

| Помилка | Повідомлення або контекст | Cause | Перевірка |
| --- | --- | --- | --- |
| Хибні поля в конструкторі | Непорожній текст, невід’ємні кількість і скінченна ціна | IllegalArgumentException моделі | SparePartRecordTest |
| Неправильна кількість CSV-полів | Очікується 5 полів | Відсутній для структурної помилки | SparePartRecordTest |
| Хибне число | Некоректні поля деталі | NumberFormatException | fromCsv та invalid.csv |
| Хибне значення, наприклад NaN | Некоректні поля деталі | IllegalArgumentException | SparePartRecordTest |
| Незакриті лапки або зайвий символ | Незакриті CSV-лапки / символ після закритих лапок | Відсутній для синтаксичної помилки | CsvParserTest |
| Невідомий заголовок | Некоректний CSV-заголовок деталі | Відсутній | SparePartRecordTest |
| Відсутній файл, каталог замість файла, хибне UTF-8 | Не вдалося прочитати CSV зі шляхом | IOException | SparePartRecordTest |
| Неможливий запис експорту | Не вдалося записати CSV зі шляхом | IOException | CsvExporterTest і MainTest |
| Немає колонок або хибна схема | Клас не має CSV-полів / некоректна колонка | Відсутній | CsvExporterTest |
| Немає доступу до поля | Назва недоступного поля | IllegalAccessException або помилка обмеження доступу | Перевірка в експортері |

Помилка предметного запису при читанні файла додатково обгортається з номером логічного CSV-запису. Для invalid.csv номер дорівнює 2. NumberFormatException залишається в ланцюгу cause. Номер логічного запису може відрізнятися від номера фізичного рядка через multiline-поля.

Приклад хибного запису з `src/test/resources/lab05/invalid.csv`:

```csv
A,Bosch,Фільтр,100,abc
```

Поле кількості `abc` не перетворюється на `int`. Метод `fromCsv` викидає `DataStorageException` із причиною `NumberFormatException`. При читанні файла `read` додає до повідомлення номер «CSV-запис 2» і зберігає початковий виняток у ланцюгу причин. Ці перевірки виконує тест `invalidNumberPreservesCauseAndMalformedFileReportsRecordNumber`.

CLI перевіряє всі пари шляхів до запису, включно з посиланнями на той самий файл. Конфлікт дає код 2. Помилка CSV-експорту дає код 1 і діагностику в stderr; старий текстовий звіт при такій помилці ще не перезаписаний. Експорт і звіт є двома окремими файловими операціями, тому збій запису звіту після успішного експорту не скасовує створений CSV.

## 15. Відповіді на контрольні питання

1. T дозволяє використовувати одне сховище для різних типів із перевіркою компілятором.
2. Параметризований клас зберігає перевірку типів, raw type її послаблює й може вимагати небезпечних приведень.
3. Predicate<? super T> дозволяє передати умову для T або його супертипу.
4. Незмінний знімок захищає список сховища й не змінюється після наступного add.
5. Checked exception потрібно обробити або оголосити в throws; DataStorageException описує невдалий імпорт чи експорт.
6. Cause зберігає технічну першопричину, наприклад NumberFormatException або IOException.
7. Path описує шлях для поточної ОС, Files читає, записує й створює каталоги без ручного складання роздільників.
8. Якщо кодування відрізняється при записі й читанні, український текст може пошкодитися; обидві операції використовують UTF-8.
9. RUNTIME залишає анотацію доступною рефлексії, FIELD обмежує її застосування полями.
10. Анотація містить метадані; експортер окремо читає їх і виконує запис.
11. getDeclaredFields повертає власні поля класу, включно з приватними. Для успадкованих полів потрібно пройти базові класи.
12. trySetAccessible може повернути false через обмеження доступу; без перевірки наступне читання поля завершиться помилкою.
13. Порядок getDeclaredFields не задає контракт CSV; сортування за Java-іменами забезпечує однакову схему.
14. split по комі розіб’є екрановану кому й не врахує multiline-поле. Парсер має стежити за станом лапок.
15. Поле зі спецсимволами береться в подвійні лапки, а кожна внутрішня подвійна лапка подвоюється.
16. У порожнього списку немає першого об’єкта, тому Class<T> передається окремо для побудови заголовка.
17. Експортер читає анотовані поля довільного класу; предметний fromCsv знає типи, порядок і правила валідації свого запису.
18. Програма розрізняє помилки моделі, синтаксису CSV, значень полів, заголовка, рефлексії й файлової системи.
19. Round-trip перевіряє відновлення всіх полів і порядку після перетворення об’єкти → CSV → об’єкти.
20. Порожній catch приховає невдалий запис чи пошкоджений файл. Помилку потрібно обробити або передати з контекстом і cause.

## 16. Висновки

Замінив накопичення деталей у списку на `Repository<T>` і додав CSV-експорт через анотацію та рефлексію. Контрольні п’ять записів із комою, лапками та багаторядковою назвою відновлюються без зміни полів і порядку. Попередній текстовий звіт збережено.

Файл, створений через `--export`, містить заголовок `артикул,виробник,назва,ціна,кількість` і записи в UTF-8. Цей CSV є входом для наступного програмного блоку обробки даних про склад. Розбір усього документа через CSV-парсер зберігає перенесення всередині назви як частину одного запису.
